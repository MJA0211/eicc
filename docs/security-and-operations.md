# Security and operations

## Deployment modes

The default configuration is a local fictional portfolio. Demo sign-in deliberately lets the visitor choose
any demonstration role, including administrator. Keep this mode on a trusted local machine. The supplied
Compose file publishes only the frontend on loopback; PostgreSQL and the backend remain on its private network.

For password-based use, set these values privately in `.env` or your deployment's secret configuration:

| Variable                   | Purpose                                                                                           |
| -------------------------- | ------------------------------------------------------------------------------------------------- |
| `EICC_DEMO_MODE=false`     | Disable the demo login endpoint and automatic project seeding                                     |
| `EICC_ADMIN_EMAIL`         | Initial administrator account email                                                               |
| `EICC_ADMIN_PASSWORD`      | Initial private password, at least 12 characters; never commit it                                 |
| `EICC_SECURE_COOKIES=true` | Send session cookies only over HTTPS                                                              |
| `EICC_ALLOWED_ORIGINS`     | JSON list containing the exact browser origin, including scheme and port                          |
| `EICC_DATABASE_URL`        | SQLAlchemy database URL for local/custom deployment; Compose supplies its internal PostgreSQL URL |
| `EICC_POSTGRES_PASSWORD`   | Private PostgreSQL password generated by `scripts/init_env.py` for Compose                        |
| `EICC_SESSION_HOURS`       | Session duration, default 8 hours                                                                 |
| `EICC_PORT`                | Compose frontend host port, default 8080; update allowed origins if changing it                   |

Terminate TLS at a trusted reverse proxy and forward to the loopback frontend. The supplied Compose file does
not provision a public domain or TLS certificate. Secure cookies cannot authenticate a plain HTTP session.

Startup runs migrations, creates the fictional organization record, and creates the configured administrator
if its email is absent. In non-demo mode it leaves the project workspace empty. Disabling demo mode on an
existing database preserves its existing project data; it does not erase the Northstar scenario.

Bootstrap is create-once: changing the bootstrap password later does not change an existing account. Remove
bootstrap values from the runtime configuration after successful account creation and restart the service.
Do not reuse example/test passwords. There are no published default credentials.

## Additional accounts

An operator with access to the application environment can create named accounts through a hidden password
prompt. The password is never supplied as a command-line argument:

```sh
uv run python -m backend.users --email analyst@example.test --name "Fictional Analyst" --role analyst
```

For Compose:

```sh
docker compose exec backend python -m backend.users --email analyst@example.test --name "Fictional Analyst" --role analyst
```

Use a real intended account identifier for your private installation. The `.test` address above is only an
example. Allowed roles are viewer, analyst, tester, stakeholder, manager, and admin. The command rejects weak
passwords and duplicate emails and writes an audit event containing the email and role, never the password/hash.
It cannot silently overwrite an existing account. Account lifecycle administration beyond initial provisioning
is an operator responsibility; this demonstration does not expose self-service reset or an email delivery service.

## Authentication, authorization, and request controls

Passwords use Argon2 via `pwdlib`. Login issues a cryptographically random opaque session cookie. The database
stores its SHA-256 token digest and expiry rather than the bearer token. Cookies are HTTP-only and SameSite
Strict; the secure flag is configurable for HTTPS. Logout deletes the server session. Expired sessions fail
authentication. Sign-in has a per-process limit of 60 attempts per minute per client address.

Authenticated browser mutations require a session-bound CSRF token and an allowed Origin when present.
Authorization is enforced by the backend. Read-only viewers cannot mutate records. Analyst/tester/stakeholder
permissions differ; requirement and change approval and release transitions require management authority.
The demo administrator can intentionally explore all capabilities. UAT stores the represented stakeholder
separately from the authenticated decision actor.

Ordinary artifact PATCH requests require an `If-Match` revision and reject stale writes with a conflict.
Workflow transitions use dedicated routes with state and business-rule validation. Pydantic rejects unknown
fields, invalid references, invalid enum values, and malformed payloads. SQLAlchemy parameterizes queries;
search escapes literal wildcards. Database constraint errors are translated into bounded API errors.

## Evidence and execution boundaries

The runner can call only fixed local simulator paths using an in-process HTTP transport. Interface metadata
does not grant arbitrary network access. Transformations are a fixed allowlist; there is no expression evaluator,
shell runner, uploaded code execution, or production credential input. XML parsing rejects unsafe constructs.
Notification recipients must use `.test` addresses and no real email is sent.

Executions, UAT results, approvals, generated document contents, and attachments are immutable through their
APIs. Fresh definitions require fresh evidence or approval as applicable. Audit events retain actor, action,
entity, time, previous value, and new value. Northstar reset deliberately removes and rebuilds its demonstration
evidence while preserving historical audit events and other projects.

Normal request bodies are limited to 256 KiB. Attachment requests allow base64 overhead up to 3 MiB, and decoded
files must be 1 byte–2 MiB. Accepted types are PNG, JPEG, PDF, and UTF-8 text. Binary signatures and text encoding
are checked; filenames are sanitized. Downloads require authentication and use attachment disposition,
`application/octet-stream`, and `nosniff`. Files live in the database and carry a SHA-256 digest.

File signature validation is not malware scanning. Audit records are not tamper-proof against database
administrators. Do not use this portfolio to store confidential production data or regulated evidence.

## Routine operations

```sh
docker compose ps
docker compose logs --tail 100 backend frontend
docker compose exec backend alembic current
```

`GET /api/health` verifies database connectivity and reports the application version and demo mode. Compose
checks database, backend, and frontend health before declaring startup successful. Startup is idempotent:
existing demo records and evidence are preserved. The application uses explicit Alembic migrations, not
`create_all`, during normal startup.

To stop without losing the database:

```sh
docker compose down
```

Do not add `--volumes` unless you intend to delete the stored database. Use the Windows stop helper when the
start helper created a WSL keepalive process. Local process IDs and logs are in the ignored `.local/` directory.

### Backup and restore

Use PostgreSQL's native tools and store the result outside the repository with appropriate file permissions.
These examples are intended for a POSIX terminal and an operator-controlled backup path:

```sh
docker compose exec -T postgres pg_dump -U eicc -d eicc --format=custom > /secure/backups/eicc.dump
```

Restore first into a separate verification environment. The command below intentionally targets an empty
verification database; supply its connection through normal PostgreSQL environment configuration:

```sh
pg_restore --dbname=eicc_restore --no-owner --exit-on-error /secure/backups/eicc.dump
```

The repository does not claim a tested enterprise disaster-recovery procedure. Review restored records,
evidence counts, migrations, and authentication before selecting any restored environment for use.

### Troubleshooting

| Symptom                                       | Check / resolution                                                                     |
| --------------------------------------------- | -------------------------------------------------------------------------------------- |
| Compose requires a password                   | Run `python scripts/init_env.py`; retain the generated untracked `.env`                |
| Port 8080 or 5173 is occupied                 | Stop the owning local service or deliberately change the port and allowed origin       |
| WSL containers disappear after a command ends | Use `scripts/start-docker.ps1`, which retains a hidden WSL process                     |
| 403 on writes                                 | Verify role, CSRF token, and the exact allowed browser origin                          |
| Login succeeds but the browser is signed out  | Secure cookies require HTTPS; check the deployment URL and configuration               |
| 409 on an edit                                | Reload the record, review the newer version, and submit with its current revision      |
| An old passing test no longer counts          | The test contract changed; execute the current definition and inspect the new evidence |
| A previous UAT decision is stale              | Review current criteria and evidence and record a fresh stakeholder decision           |
| A release cannot become Ready                 | Open Readiness and address each failed mandatory gate in its actual source record      |
| An intentional seed failure remains           | Follow the investigation guide; changing a status label cannot repair the contract     |

## Security scope

Roles are organization-wide, not tenant or project isolation. The deployment does not implement SSO/MFA,
distributed throttling, malware scanning, a broker, high availability, external secret rotation, or compliance
certification. These are explicit portfolio boundaries. The implemented authentication and input controls are
tested, including non-demo login, role rejection, expiry, CSRF, origin/body limits, safe XML, and session revocation.
